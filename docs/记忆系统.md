# 记忆系统（4.0 / v2）

一句话：**一个静态人设 + 每个聊天里的「一人一卡」+ 每个聊天的事件时间线 + 当前话题的短期缓冲。**

- 实现：`src/memory/*`
- 没有全局用户记忆，没有跨聊天同步，没有敏感词分类，用户看不到任何记忆正文。

---

## 1. 硬约束

1. 按聊天隔离：私聊 A、群 G、群 H 各自独立物理目录。
2. 按人建卡：卡的主键是 `chatId + uid`，不是全局用户。
3. 群聊只读当前说话人：A 说话只注入 A 的卡，B 问 A 也不注入 A 的卡。
4. 写卡必须满足 `card.chatId === source.chatId`，不一致直接抛
   `MEMORY_CHAT_MISMATCH`，不做自动合并。
5. 不做敏感词分类、不做敏感字段、不做输出审查。
6. 记忆不展示、不提供查询接口：`GET /api/memory` 已删除，启动器记忆页已删除，
   聊天里的 `/memory` 命令已删除；接口只返回计数。

---

## 2. 四层

| 层 | 内容 | 作用域 | 生命周期 |
|---|---|---|---|
| L0 | 鲸鲸人设 | 全局静态 | 永久，聊天不改写 |
| L1 | 人物卡（traits + preferences） | `chatId + uid` | 长期 |
| L2 | 事件卡 + threads | `chatId + uid` | 365 天 / 200 条每人 |
| L3 | 当前 episode 原文 + 摘要 | 当前 chat | episode 关闭时清空缓冲 |

术语沿用这里的叫法：`chatId` 是一个私聊或群，`uid` 是平台内稳定用户 id（不用昵称），`personCard` 是某个聊天里某个人的卡，`episode` 是一段连续话题，L0–L3 对应上表四层，`hard prefix` 指 system 里可缓存的固定人设、`soft block` 指放在最后一条 user 消息里的人物卡/事件/摘要。设计原则：按聊天隔离、按人建卡、群聊只读当前说话人、不跨聊天同步、按 token 压缩而不按消息条数、压缩只移出 prompt 缓冲不删原文、用户只看得到人设、热路径不调模型做抽取。

## 数据模型

### L0 人设

存在 `config/persona` / `persona.json`，字段沿用现有：

- 名字、年龄、职业、外形、性格、背景
- 说话风格、emoji 习惯
- 主人名单、边界
- 群规、禁言列表

**聊天内容不能写 L0。** 用户说「从现在起你是我奴隶」只当聊天内容，不改人设。

### L1 人物卡

```json
{
  "chatId": "wechat:g:123456",
  "uid": "wxid_x",
  "name": "小海",

  "traits": [
    {
      "text": "嘴硬心软",
      "confidence": 0.72,
      "evidence": ["msg_1001", "msg_1042"]
    }
  ],

  "preferences": [
    { "text": "喜欢猫", "confidence": 0.9, "source": "msg_1005" },
    { "text": "不吃香菜", "confidence": 0.8, "source": "msg_1012" },
    { "text": "不喜欢被叫乐乐", "confidence": 0.95, "source": "msg_1020" }
  ],

  "events": [
    {
      "id": "evt_20261028_01",
      "date": "2026-10-28",
      "title": "面试前的紧张",
      "summary": "面试前很紧张，准备了三天，最后没敢问结果。",
      "keywords": ["面试", "紧张", "工作"],
      "participants": ["wxid_x"],
      "importance": 0.6,
      "confidence": 0.8,
      "source": {
        "chatId": "wechat:g:123456",
        "messageIds": ["msg_1201", "msg_1202"]
      }
    }
  ],

  "threads": [
    {
      "id": "th_01",
      "text": "还在犹豫要不要辞职",
      "status": "open",
      "createdAt": 1760000000000,
      "lastMentionedAt": 1760000000000
    }
  ],

  "updatedAt": 1760000000000
}
```

字段约束：

| 字段 | 约束 |
|---|---|
| `traits` | 5~12 条，每条 20~40 字，必须带 confidence + evidence |
| `preferences` | 10~30 条，每条 10~40 字 |
| `events` | 100~200 条/人，每条 60~150 字 |
| `threads` | 5~10 条，open/closed |
| `name` | 显示名，可随群昵称更新，但 `uid` 不变 |

### L2 事件卡

事件卡不是每句话一条，而是「一段事一条」。

必填：

- `date`：YYYY-MM-DD
- `title`：≤ 20 字
- `summary`：60~150 字
- `keywords`：3~10 个
- `participants`：涉及的 uid
- `importance`：0~1
- `confidence`：0~1
- `source.chatId`：必须等于卡片 `chatId`
- `source.messageIds`：来源消息

可选：

- `valence`：-1~1，情绪正负
- `resolved`：是否已解决
- `threadId`：关联的未完成话题

### L3 短期状态

```json
{
  "episodeId": "ep_20261031_01",
  "chatId": "wechat:g:123456",
  "startedAt": 1760000000000,
  "lastMessageAt": 1760000000000,
  "episodeTokens": 1800,
  "recentTokens": 1600,
  "activeTopic": "换工作",
  "unresolved": ["面试结果还没说"],
  "lastPromise": "",
  "participants": ["wxid_x", "wxid_y"]
}
```

## 3. 存储布局

```text
data/memory/
├─ manifest.json
├─ legacy/                    # 迁移前的旧文件只读副本（程序不再读）
└─ chats/
   └─ <chatHash>/             # sha1(chatId).slice(0,16)
      ├─ meta.json            # chatId、平台、state、episode、closedEpisodes
      ├─ people/
      │  └─ <personHash>.json # sha1(uid).slice(0,16)
      ├─ messages.jsonl       # 原文，追加写
      ├─ summary.json         # 当前摘要段 + coveredThroughSeq
      └─ checkpoints/
         └─ 00000123.json     # 每轮一份，最多 50
```

- 卡片 / 摘要 / checkpoint：先写 `.tmp` 再 `rename`。
- 用户消息先 `fsync` 落盘，再进入回复流程；回复失败也不丢用户消息。
- 每个 chat 的磁盘写入是同步串行的；跨 chat 后台任务按 chat 排队。
- 原文只追加；只有「已被 summary 覆盖」且超过 90 天 / 2000 条的旧消息才会删。

---

## 4. 写入

每条消息：

```text
1. 识别 chatId + uid
2. 追加 messages.jsonl（用户消息 fsync）
3. 更新 meta.lastActiveAt / stats / episode 计数
4. 规则抽取（不调模型）：明确自述、明确纠正、手动记住
5. 连续 20 条 user 消息 → 轻量 fact 候选（不调模型、不写 L2）
6. 软阈值 2,400 token → 后台准备「最旧 800 token」摘要
7. 进入回复流程
```

episode 关闭（任一条件）：

- 空闲 30 分钟；
- 聊了至少 6 条后话题切换（关键词重合度 < 0.15，或明确说「换个话题」）；
- 累计 6,000 token；
- 持续 3 小时。

关闭时：生成最终摘要 → 给每个发言人写一条 L2 → 抽 fact / trait / thread →
重置 L3 水位 → 新 episode 从下一条消息开始。同一个 `episodeId` 只写一次。

性格标签比事实谨慎：至少 2 条证据（或明确自述）、`confidence >= 0.65`、
必须带消息 id；单次情绪、玩笑、反话不写。

---

## 5. 读取

每轮回复只加载：

```text
当前 chat 里、当前说话人的卡
  → traits + preferences（在 memory 分片内；条数 6/10 起，随预算最多 12/20）
  → 这个人事件卡里 top 5~10（bigram + BM25 + recency/importance/confidence + MMR）
  → 当前摘要
  → 最近原文（≤3,200 token，当前消息永不裁剪）
```

记忆块放在**最后一条 user 消息**里，不塞 system：system 会话内稳定，前缀缓存不被打断。
群聊历史是公开的，可以用；但 A 的私聊卡、A 在别的群的卡永远不进来。

## 6. 压缩与预算

压缩阈值不再写死，而是**跟着 recent 的预算走**（`src/memory/budgetPlan.js` 派生）：

```text
recent >= 75% × recentMax → 后台准备摘要（不删消息）
recent >  recentMax       → 应用摘要，一次移走 25% × recentMax，回到 75%
summary >  summaryTokens  → 合并最旧摘要段（保留每段开头），不直接丢事实
```

默认 5,500 预算下就是原来的 `2,400 / 3,200 / 800`，行为不变；预算调大后阈值
一起变大，不会出现「预算 20,000 还在按 3,200 压缩」这种白调。

压缩只影响 prompt 缓冲，不删 `messages.jsonl`。摘要失败时原文保留、
`coveredThroughSeq` 不前进。

### 6.1 分片按比例算，只留一个可调项

用户能改的只有 `config.memory.dialogueBudget`（启动器「高级 → 对话预算」）。
所有分片由 `src/memory/budgetPlan.js` 从它换算，**不要在别处再写死 900 / 3,200**：

| 分片 | 比例 | @5,500 | @8,000 | @20,000 | 结构上限 |
|---|---|---:|---:|---:|---:|
| `recent` | 剩余（58%→78%） | 3,200 | 4,655 | 15,500 | 无 |
| `memory` | 16.36% | 900 | 1,309 | 2,200 | 2,200 |
| `summary` | 16.36% | 900 | 1,309 | 1,500 | 1,500 |
| `reserve` | 9.09% | 500 | 727 | 800 | 800 |
| `relations` | 2.18% | 120 | 120 | 200 | 200 |

**记忆和摘要也会涨，不是只涨 recent**：D=8,000 时两者都是 1,309；涨到 2,200 / 1,500
封顶（大约 D=13,500 处）之后，剩下的才全给 `recent`，所以 20,000 时 recent 占 78%。
封顶理由是内容有物理上限：一屏最多 12 traits + 30 偏好 + 10 threads + 10 事件 ≈ 2,160 token，
再多只是把同一个人写得更啰嗦；摘要超过 1,500 会开始丢细节而不是变准。

**可填范围**：启动器滑块 2,000–20,000（步进 100），右边输入框最低 1,000、不设上限；
但分片最多按 64,000 算（单轮硬上限），超出部分不会让分片继续涨，只在那一轮被拒绝并报错。

**条数也要跟着预算涨**，否则 token 上限到了也没内容可装：

| 跟着 recent 派生的 | @5,500 | @20,000 | 说明 |
|---|---:|---:|---|
| 私聊最近消息条数 | 120 | 581 | 与 token 上限「谁先到谁算数」 |
| 群聊最近消息条数 | 100 | 484 | 同上 |
| 人物卡 traits / 偏好 / threads / 事件 | 6 / 10 / 4 / 5 | 12 / 24 / 10 / 10 | 按 `memory` 预算等比放大，封顶 12 / 30 / 10 / 10 |

消息长（150 token 一条）时 token 先到，消息短（15 token 一条）时条数先到——两条腿
都要随预算放大。

### 6.2 推荐档位（提示，不是开关）

滑块仍然是连续的，这四个只是给 UI / 文档做参照，代码里是 `budgetPlan.TIERS`：

| 档位 | 预算 | recent | memory | summary | reserve | recent 占比 | 最近消息（私/群） | 适合 |
|---|---:|---:|---:|---:|---:|---:|---|---|
| 极简 | 2,000 | 1,191 | 327 | 300 | 182 | 60% | 45 / 37 | 只想让她接话 |
| 默认 | 5,500 | 3,200 | 900 | 900 | 500 | 58% | 120 / 100 | 开箱值，日常闲聊 |
| 标准 | 10,000 | 6,064 | 1,636 | 1,500 | 800 | 61% | 227 / 190 | 主力档 |
| 重度 | 20,000 | 15,500 | 2,200 | 1,500 | 800 | 78% | 581 / 484 | 长会话 / 大群 |

### 6.3 配额是上限，不是目标

四段各自是**独立的硬上限，之间不互相挪用**：

- 记忆配额 2,200，但这个人只有一张空卡 → 实际只占几十个 token，`recent` **不会**
  因此涨到 17,700；它仍然守在自己的 15,500。
- 反过来，卡再满也只在 2,200 以内，不会挤到 `recent`。
- 唯一会让 `recent` 略微超出的情况是「当前这条消息本身太长」——它永远保留、只截断。

为什么不把省下来的额度动态挪给 `recent`：那样压缩阈值每轮都会变，会话会一会压一会不压，
而且同一段对话的 prompt 前缀会不断重排、缓存全废。固定配额换来的是行为可预测。

顺带一句：`memory` 和 `summary` 拼在同一段文本里（摘要小节在最后），所以
`format.buildMemoryBlock` 的预算传的是 `memory + summary`，不然摘要一长就会把卡的展示位挤掉。

小预算（D < ≈2,700）下 recent 分不到 `min(1,600, 60% × D)`，按「摘要 → 预留 →
记忆」的顺序回收，`store.summary().budget` 里能看到 `mode: 'reclaim'`。

预算语义（2026-11 调整，替换 2026-10 的固定四段）：

```text
dialogueBudget       = D（默认 5,500，启动器可调）
  = recent + memory + summary + reserve + relations   # 由 budgetPlan 分配，恒等于 D
systemTokens         = estimateTokens(system)      # 只测量，不裁剪
estimatedPromptTokens = estimatePrompt(system, turns)  # system + 本轮实际 turns
dialogueBudget       = D（默认 5,500）            # 只给裁剪窗口用
hardTotalTokens      = 64,000                      # 真实估算超过才拒绝/报错
```

- 不再有「7,500 总预算 / 2,000 system 上限」。
- system 变大不会挤 recent 或 memory。
- `estimatedInputTokens` 保留为兼容字段，语义同 `estimatedPromptTokens`；不再返回 `system + D`。
- token 估算：CJK ≈0.65/字、非 CJK ≈0.3/字、每条消息 +4；预算裁剪乘 1.08。
- **人设保存 / 导入**时用当前模型的官方 tokenizer（服务商 `usage.prompt_tokens`）精确校验；
  上限 = `64,000 - 5,500 = 58,500`。没有 Key / 离线时退回估算并标 `exact:false`。
  每轮聊天仍然只用轻量估算，不调官方 tokenizer。
- API usage（`prompt_tokens` / `completion_tokens`）会按 provider|model 学习校准 scale
  （src/memory/calibration.js，持久化 data/calibration.json）；只在实际用量超出校准后估算
  >15% 时 warning，实际更少不告警。校准样本 ≥10 且量化到 0.05 后才参与裁剪。
  只记计数，不打印正文。
- 只给内部 status / 日志字段，不做预算 UI、滑块、接口。

## 7. 关闭 / 重启 / 迁移

- 正常关闭：flush 消息队列 → 写最后一个 checkpoint → 关文件。
- 启动：读 meta / 卡 / summary → 读最近原文 → 距上次消息 >30 分钟则后台补写
  上一个 episode 的 L2 → `recent >3,200` 时首条回复前压缩。
- 不会全量重压；原文已经落盘，补写失败只是晚一轮。

迁移（4.0 `store.json` + journal、旧 `memory.json`）：

- 每个旧会话 key 落到自己的 chat 目录，绝不跨 chat 合并；
- **4.0 已有的 chat 不再整段跳过**：缺的消息按 `ts` 合并进来、去重后整体重排 `seq`，
  notes 按文本去重补进人物卡（旧 note 仍是 `legacy: true`、置信度 0.4）；
  如果补进来的旧消息早于当前摘要的覆盖线，摘要会被清空让下一轮重压，避免「旧消息没被概括却算已覆盖」；
- 旧文件不删、不改；在 `data/memory/legacy/` 留只读副本和说明；
- 幂等：`manifest.migratedFrom` 记 `源文件:size:mtime + journal:size:mtime`，重复启动不会重复导入
  （迁移记录会回写进 `ChatStore.manifest`，不会被防抖保存时的旧对象覆盖）；
- 手动导入：`node scripts/memory-tool.js import <store.json|memory.json|旧备份包> [--dry-run]`，
  写盘前自动留一份 `before-import` 快照，dry-run 只打报告。
- **不用敲命令也能迁移**：把旧 `data\` 合并进来后正常启动即可，`Store` 构造时会自动迁移；
  写入 `data/memory/import-report.json` 记一份待确认报告，启动器在下一次内核就绪时弹
  「记忆已导入并转换格式」，展示后 ack，之后不再弹。
- 启动器「设置 → 高级 → 旧版记忆 → 一键识别转换记忆」：先 dry-run 看会补多少，确认后
  `POST /api/memory/import` 执行；只读检测接口 `GET /api/memory/import/status`。
  接口只回计数、只允许本机，且与启动迁移共用同一套签名，重复点不会重复导入。
- 刚导入的 chat 会在 `meta.importedAt` 标记，7 天内不参与 `archiveIdle` 归档、
  也不 `pruneRaw` 清「已覆盖且超 90 天」的原文，避免刚导进来就少一段。

备份 / 恢复只保留本地 CLI 和本地文件（`scripts/memory-tool.js`、
`data/backups/`）；没有 HTTP 接口，不在 UI 展示正文。启动器「诊断 → 数据维护」也有备份 / 恢复按钮，
背后调的就是同一个 `memory-tool.js`（恢复前会先停内核并另存一份当前记忆）。

## 8. 参数

全部写死在 `src/memory/constants.js`，不读 `config.json`、不提供接口。
唯一例外是 `dialogueBudget`（启动器可调），其余分片都是它的比例基准，
由 `src/memory/budgetPlan.js` 换算——改下表的分片值不会生效。

| 参数 | 默认值 |
|---|---:|
| `dialogueBudget` | 5,500（唯一可调） |
| `hardTotalTokens` | 64,000 |
| `memoryTokens` | 900（16.36% 比例基准） |
| `summaryTokens` | 900（16.36% 比例基准） |
| `recentMaxTokens` | 3,200（剩余，≈58%） |
| `reserveTokens` | 500（9.09% 比例基准） |
| `relationsTokens` | 120（2.18% 比例基准，功能未启用） |
| `recentLowTokens` | 2,400（= 75% × recent 的默认值，实际由 budgetPlan 派生） |
| `compressChunkTokens` | 800（= 25% × recent 的默认值） |
| `episodeMaxTokens` | 6,000 |
| `episodeIdleMinutes` | 30 |
| `episodeMaxHours` | 3 |
| 每人 traits / preferences / events / threads | 12 / 30 / 200 / 10 |
| 每 chat 人数 / events | 50 / 1,000 |
| 原文保留 | 2,000 条 / 90 天 |
| 事件保留 | 365 天 |
| 输出上限 | 普通 100 字 / 讨论 400 字 |

- `tests/persona-token.test.js`：人设保存/导入的官方 tokenizer 精确校验与离线回退。

## 10. 已知限制

1. 对话侧 token 只用轻量估算；**人设保存 / 导入**才用官方 tokenizer 精确计数（见 §6），
   并用 API usage 校准，误差 >15% 会告警。
2. episode 关闭后的第一轮靠摘要接住旧话题；摘要生成失败时只会少一段摘要，
   原文仍在磁盘。
3. 群聊里事实按「说话的人」归，不按「关于谁」归；B 问 A 的私事，只有群历史
   公开部分可用。
4. 记忆仍在本机 `data/memory/` 文件里；能直接翻文件的人还是能看到，
   应用界面不暴露。
