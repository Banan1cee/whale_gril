# 回归测试覆盖对照（release ↔ 测试）

> 目的：**换架构的时候，能一眼看出「这条修过的问题有没有人守着」**。
> 每次发版补一条测试，就在下表加一行；`tests/bug-ledger.test.js` 会自动检查
> `BUGS.md` 里的引用是否真实存在（台账里的路径写错、被转义坏掉，都会红）。

## 一、CI 现在跑什么

`.github/workflows/tests.yml`（`windows-latest`，Node 24 + Python 3.12 + .NET 10），
每一步都带 `if: always()`，一次运行看完所有结论：

| # | 步骤 | 守的是什么 | 需要微信/密钥 |
| --- | --- | --- | --- |
| 1 | `node scripts/check-layers.js` | 分层依赖（core 不许 require 上层） | 不需要 |
| 2 | `node scripts/release-check.js` | 出包自检 24 项（版本号、包里真有的功能、无个人信息…） | 不需要 |
| 3 | `npm test` | `tests/*.test.js` 全量（当前 745 条） | 不需要（全部 mock） |
| 4 | `python -m unittest discover` | 桥接侧逻辑（`tests/test_*.py`，当前 90 条） | 不需要 |
| 5 | `scripts/bg-selftest.py` + `scripts/bridge-pipeline-selftest.py` | 零焦点发送编码、按会话串行/跨会话调度 | 不需要 |
| 6 | `dotnet build launcher` | 启动器 WPF 能编译 | 不需要 |
| 7 | `node server.js --doctor` | 起得来、自检不报错 | 不需要 |

第 5 步是本次补上的：这两个自检 3.56/3.57 就写好了，但一直只在开发机上手动跑，
谁动了 `bridge/` 的编码或调度，只有真机才会发现。

## 四、还没有自动化覆盖的部分（诚实清单）

| 区域 | 为什么现在测不了 | 现在靠什么 |
| --- | --- | --- |
| 微信 UIA 真机发送 / 抢前台 | 需要装微信、登录、管理员权限，CI 机器没有 | 手动 + `一键诊断UIA.bat` + `tests/test_*.py` 的 mock 行为测试 |
| 启动器 WPF 的交互（点按钮、拖拽） | CI 只编译，不跑 UI | `tests/launcher-ui.test.js` 静态断言 XAML / 资源键 |
| 出包（zip 内容、sha256、回滚） | 需要 100MB+ 产物 | `scripts/release-check.js` 静态检查 + 手动出包 |
| 天气 / 联网真实结果 | 受搜索引擎验证码、平台风控、模型误判影响 | 全部走 fixture；只保证「代码路径正确」，不保证「一定搜得到」 |
| 记忆的语义质量（她记不记得住） | 需要真实模型打分 | `tests/memory-eval.test.js` 的离线评测集 |

> 结论：**代码缺陷类**的回归基本齐了（90 条左右的正向用例盯着 `BUGS.md` 里的历史问题），
> 缺的是「真机 / 真模型」那一层，那一层不可能在 GitHub Actions 上做。
