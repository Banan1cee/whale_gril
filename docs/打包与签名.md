# 打包与签名（安装包都在 GitHub Actions 上打）

本机**不再出安装包**。安装包由 `.github/workflows/installer.yml` 在 GitHub 的
`windows-latest` 上构建：Python 与 Node 打进包里，.NET 10 桌面运行时随包、目标机缺失时
安装器请求管理员授权后静默安装。这样做换到三件事：

1. **能签名**：证书只放在仓库 secrets 里，构建机签完就删，私钥不落地到本机。
2. **出包可追溯**：谁、哪次提交、哪个版本出的包，在 Actions 运行记录里都有。
3. **本机干净**：不用为了出包装 Inno Setup / Python / Node，也不用把 200MB 产物存本地。

---

## 一、流水线做了什么

`installer.yml` 一个 job 跑完，全部在 Windows runner 上：

| 步骤 | 做什么 | 产物 / 检查点 |
| --- | --- | --- |
| 环境 | setup-node 24、setup-python 3.12、setup-dotnet 10.0.x | 版本打印进日志 |
| 解析版本号 | tag 去 `v` → `workflow_dispatch` 手填 → `package.json` | 归一成 `x.y.z`，写进 `GITHUB_ENV` |
| 构建运行环境 | `scripts/build-runtime.ps1`：取 node.exe、解 CPython 3.12 embeddable、离线装桥接依赖 | `runtime\node.exe`、`runtime\python\`、`runtime\manifest.json` |
| .NET 运行时 | `scripts/fetch-dotnet-runtime.ps1`：从 aka.ms 下载，**校验 Authenticode 签名确实是微软** | `runtime\dotnet\windowsdesktop-runtime-10-win-x64.exe` |
| 启动器 | `dotnet publish`（framework-dependent 单文件） | `launcher\publish\WhaleLauncher.exe` → 覆盖根目录那份 |
| 签启动器 | SignPath（`SIGNING_MODE=signpath`）或 `scripts/sign-windows.ps1`（PFX）；签完立刻回读 `Valid` | **必须在编译安装包之前**，否则包里嵌的是未签名 exe |
| 安装器 | 用仓库自带的 Inno Setup 7.1.1（`installer/innosetup/`，缺了才联网下），`ISCC --define=AppVersion=<版本> installer\whale.iss` | `artifacts\setup\whale-girl-<版本>-setup.exe` |
| 签安装包 | 同一条签名路线，签 setup.exe | 配了 `SIGNING_MODE` 时签不上直接红 |
| 安装烟测 | 静默装到临时目录 → 逐个核对文件 → 跑一次 `import` → 静默卸载 | 见下方「烟测查什么」 |
| 上传 | Artifact `whale-girl-setup-<版本>`，含安装包与 `SHA256SUMS.txt` | 保留 30 天 |
| Release | 只有 tag 触发才建 | `gh release create`，挂了才 `--clobber` 补传 |

「构建运行环境」这步要装约 380MB 的 Python 依赖，首次约 6–10 分钟，所以加了
`actions/cache`（缓存 `runtime\python` 和 `node.exe`）。改了 `build-runtime.ps1` 里钉的
依赖版本、但 CI 好像还装着老版本时，把 `installer.yml` 顶部的 `RUNTIME_CACHE_VERSION`
加一，强制重建。

Inno Setup 7.1.1 的官方安装包也带在 `installer/innosetup/`（14.3MB，官方 license 允许二进制
再分发）：CI 直接用仓库里这份，版本钉死、不依赖网络，仓库里没有时才回退下载。升级步骤见
`installer/innosetup/README.md`。它只是构建工具，不会进用户的安装包。

### 烟测查什么

只量 exe 大小证明不了「包里真的有 Python」。烟测会把安装包真装一遍，然后核对：

- `WhaleLauncher.exe`、`server.js`、`src\core\master.js`、`bridge\engine.py` 都在
- `runtime\node.exe`、`runtime\python\python.exe`、`runtime\manifest.json` 都在
- `runtime\dotnet\windowsdesktop-runtime-10-win-x64.exe`：**在，或者被安装器删掉了且本机已有 .NET 10 桌面运行时**
  - 装完即删是设计：本机已有 .NET 10 时，那个 57MB 的安装包没必要留在用户目录里
    （见 `installer/whale.iss` 的 `CurStepChanged`）。runner 上装了 .NET 10 SDK，所以这一步基本都会走「删掉」
  - 只有「文件不在**且**本机也没有 .NET 10 桌面运行时」才判失败——那说明它压根没进包
- **`runtime\wheelhouse` 不在**（构建缓存，混进来白多 117MB）
- 包内 `node.exe -v` 能跑
- 包内 `python.exe` 能 `import wechatauto, psutil, win32com, uiautomation`

任一条不过，这次运行就红，不会产出「看着有包、装完用不了」的安装包。

## 二、怎么触发

**手动（日常出包）**

1. 仓库 → Actions → 左侧 `installer` → `Run workflow`
2. 版本号留空就用 `package.json` 的版本；要覆盖就填 `4.0.0` 这种
3. 跑完在本次运行页面底部 Artifacts 下载 `whale-girl-setup-<版本>.zip`

**打 tag（发版）**

```powershell
git tag v4.0.0
git push origin v4.0.0
```

tag 触发时版本号取自 tag（`v4.0.0` → `4.0.0`），CI 生成 `whale-girl-release-<版本>` 资产包，
包含安装包、`SHA256SUMS.txt` 和 `release-manifest.json`，不会由机器人创建公开 Release。
发版人确认构建、安装与覆盖升级检查成功后，下载资产并核对 SHA256，再用自己的 GitHub 账号创建
Release 草稿、上传这三个文件。回读核对 tag、版本、作者和附件后公开发布；同一 tag 只保留一个 Release。

> 推送与发版前先自查：`git status`、`git log`、要推的分支与 tag。规则见 `~/.dsh/AGENTS.md`。

### 发版后把更新清单提交回 main（选的是人工步骤）

清单有两条回仓库的路，这里选 **B：发版人手工提交**。CI 不自动提交——tag 构建每次都要产生一次
机器人提交，和分支保护 / 其它流水线撞车的风险不值得，而且发版本来人盯着。

> A 是 CI 用 `github-actions[bot]` 提交（要有 `contents: write`，仓库现在有）。哪天想换成自动的，
> 把下面命令换成 workflow 里一个只 add `release-manifest.json`、commit message 固定
> `release: 更新清单到 <版本>` 的 step 即可；测试 `tests/update-chain.test.js` 两种做法都兼容。

Release 里的 `release-manifest.json` 是流水线按本次版本现生成的（`latest` = 本次版本，
`released_at` = 构建时间 UTC，`manifest_version` = 仓库当前值 +1）。发版后：

```powershell
gh release download v4.0.5 -p release-manifest.json -O release-manifest.json --clobber
git add release-manifest.json
git commit -m "release: 更新清单到 4.0.5"
git push
```

不做这一步，客户端四个更新源里那两个读 `main` 分支原文的源会一直指向旧版本（Release 资产那条
会顶上来，但 raw / jsDelivr 源仍然落后，断网回退到缓存时体验不一致）。

### 发 4.0.5 的发布清单

1. `npm run bump -- "..."` 到 4.0.5，`CHANGELOG.md` 有 4.0.5 段（安装包 + 更新 + 发版三类）。
2. 提交并合并到 main（先跑 `node scripts/release-check.js`、`node scripts/check-layers.js`）。
3. 打 tag `v4.0.5` 并推送（**推送前先问用户**）。
4. CI 跑完核对三件事：
   - Release 资产 = `whale-girl-4.0.5-setup.exe` / `SHA256SUMS.txt` / `release-manifest.json`；
   - manifest 里 `latest=4.0.5`、`manifest_version` 比上一份大；
   - 「安装烟测」和「覆盖升级烟测」都绿。
5. manifest 按上一节的人工步骤提交回 main。
6. 真机回归：装一次 4.0.1 旧版，不改任何设置直接跑 4.0.5 安装包，确认能覆盖安装、能启动，
   原来的 Key 与聊天记忆都在。

## 三、版本号

- 版本号只认一处：`package.json` 的 `version`（tag / 手填优先于它）。
- `x.y` 会自动补成 `x.y.0`（`4.0` → `4.0.0`），因为 Inno 的版本资源要三段式。
- 产物名固定 `whale-girl-<版本>-setup.exe`，安装包属性里的文件版本 = 这个版本。

## 四、签名（两条路线，由仓库变量 `SIGNING_MODE` 切换）

流水线里签名是个开关，`Settings → Secrets and variables → Actions → Variables` 里加一个
**变量**（不是 secret）：

| `SIGNING_MODE` | 走哪条路 | 需要配什么 |
| --- | --- | --- |
| `signpath` | SignPath.io 免费 OSS 签名（要求 OSI 许可；本项目 AGPL-3.0 符合） | 1 个 secret + 3 个变量，见下 |
| `pfx` 或留空 | 自备 PFX 证书（老路子，仍然可用） | 2 个 secrets |
| 留空且没 secrets | 不签名，摘要里写明「未签名」 | 无 |

配了 `SIGNING_MODE` 却签不上，流水线会**直接红**（摘要那步会检查
`Get-AuthenticodeSignature` 是不是 `Valid`），不会悄悄把未签名包发出去。

### 4.1 SignPath（免费，公共仓库 OSS）

申请：<https://signpath.org/> → Apply for SignPath Foundation（免费给符合 OSI 开源许可的项目，要审核几天，
要求仓库公开、构建在 GitHub-hosted runner 上）。通过后会拿到 Organization、Project 和一个
API token（在 SignPath 后台 → 用户设置 → API tokens，权限选提交签名请求）。

> 本项目自 4.0.x 起采用 AGPL-3.0-only，属于 OSI 认可的开源许可证，符合 SignPath 对许可证的前提。
> 仍需满足公开仓库、GitHub-hosted runner、可复现构建和每次发布人工审批等条件。

**申请前仓库里必须先具备的东西**（SignPath Foundation 的硬性条件，缺了会被打回）：

1. 仓库首页（`README.md`）有「**Code signing policy**」段落，写明
   “Free code signing provided by SignPath.io, certificate by SignPath Foundation”
2. 一份完整的策略文件 [CODE_SIGNING_POLICY.md](CODE_SIGNING_POLICY.md)：签哪些文件、
   什么时候签、**团队角色**（Authors / Reviewers / Approvers 各是谁）、**隐私政策**（链接到仓库根目录唯一版本）、怎么验证签名
3. artifact configuration 里用 **file metadata restrictions** 约束 `product-name` /
   `product-version` / `company-name`（见 `.github/signpath/*.xml`），版本号由 CI 通过
   `parameters` 传 `version`，保证每次构建一致
4. 全部构建都在 GitHub-hosted runner 上跑（本仓库满足）

**要配的东西**（仓库 → Settings → Secrets and variables → Actions）：

| 类型 | 名称 | 值 |
| --- | --- | --- |
| Secret | `SIGNPATH_API_TOKEN` | SignPath 后台生成的 API token |
| Variable | `SIGNPATH_ORG_ID` | SignPath 里的 Organization ID（UUID） |
| Variable | `SIGNPATH_PROJECT_SLUG` | Project 的 slug，比如 `whale-gril` |
| Variable | `SIGNING_MODE` | `signpath` |

**SignPath 后台里要建的对象**（slug 必须和 CI 里一致，对照表见
`.github/signpath/README.md`）：

| 对象 | slug | 内容 |
| --- | --- | --- |
| Artifact configuration | `whale-launcher` | `.github/signpath/whale-launcher.xml` 的内容 |
| Artifact configuration | `whale-setup` | `.github/signpath/whale-setup.xml` 的内容 |
| Signing policy | `release-signing` | tag 触发时用（**必须配成人工审批**） |
| Signing policy | `test-signing` | 测试分支用，签完只出 Artifact |

再把 `whale-gril` 这个 Project 关联到 **Trusted Build System: GitHub.com**（SignPath 后台
按它的文档操作），并安装 [SignPath GitHub App](https://github.com/apps/signpath)。

**流水线怎么签的**（两轮，`installer.yml` 里已经写好）：

1. 编出启动器 → `upload-artifact`（**`archive: false`**，传裸 exe）→ 提交签名请求 →
   等它签完下载回来 → 覆盖根目录和 `launcher\publish` 那份 → 立刻回读校验 `Valid`
2. 编安装包 → 同样上传 → 签 → 覆盖 `artifacts\setup` 里的 → 再跑烟测 → 上传 / 发 Release

为什么分两轮：安装包里嵌的是启动器，**必须先签启动器再压安装包**，否则包里还是未签名的那份。
Inno 的压缩数据 SignPath 也改不了，所以不能先压包再签里面的东西。

### 4.2 PFX 证书（`SIGNING_MODE=pfx` 或留空，有 secrets 就签）

代码在 `scripts/sign-windows.ps1`，加两个 secrets 即可：

1. `WINDOWS_SIGNING_PFX_BASE64`：
   `[Convert]::ToBase64String([IO.File]::ReadAllBytes('D:\cert\whale-codesign.pfx'))`
2. `WINDOWS_SIGNING_PFX_PASSWORD`：PFX 的密码

签名顺序同上（启动器先签 → 编包 → 签安装包），证书只在构建机上临时落盘，`finally` 里删掉。

> ⚠️ 现实中注意：2023 年 6 月起 CA/B 论坛要求 OV/EV 代码签名证书的私钥放在硬件 token /
> HSM 里，**新签发的证书基本给不出 PFX**。所以这条路只在两种情况下顺：手上有老的
> 可导出 PFX，或者用的是厂商云签名（SSL.com eSigner、DigiCert KeyLocker）——那种要把本
> 脚本换成厂商的接口。

### 4.3 证书/服务怎么选

| 方式 | 能不能直接进 CI | 说明 |
| --- | --- | --- |
| SignPath Foundation | ✅ 符合许可证前提 | 要求 OSI 开源许可；本项目 AGPL-3.0 符合，仍需满足公开仓库与可复现构建 |
| Azure 可信签名（Trusted Signing） | ✅ 但要另写步骤 | 约 $9.99/月，Azure 订阅 + 身份审核，用 `azure/trusted-signing-action` |
| OV 代码签名证书（PFX） | ⚠️ 新证书基本给不出 PFX | 得用厂商云签名；SmartScreen 还要攒信誉 |
| EV 代码签名证书 | ⚠️ 硬件 token / 云签名 | 无信誉积累期，但要长期月费 |

> 提醒：签名≠立刻不弹 SmartScreen。新的 OV 证书有信誉积累期；EV、Azure 可信签名、
> SignPath 用的证书没有这个积累期（也就是装上就安静）。这是微软的策略，不是包的问题。

### 4.4 想强制要求签名

配了 `SIGNING_MODE` 就已经是强制的了（签不上就红）。只想让 PFX 路线也强制的话，
给 `scripts/sign-windows.ps1` 加 `-Require`。

## 五、产物与怎么验

| 位置 | 内容 |
| --- | --- |
| Actions 运行页面 → Artifacts | `whale-girl-setup-<版本>.zip`（安装包 + SHA256SUMS.txt） |
| tag 构建 → Artifacts → `whale-girl-release-<版本>` | 安装包 + SHA256SUMS.txt + release-manifest.json，由发版人校验后以自己的账号发布 |
| 运行摘要（Summary） | 版本、大小、SHA256、安装包与启动器签名状态、内置 Node/CPython 版本 |

本地验证：

```powershell
Get-FileHash .\whale-girl-4.0.0-setup.exe -Algorithm SHA256   # 对上摘要里的值
Get-AuthenticodeSignature .\whale-girl-4.0.0-setup.exe | Format-List Status, SignerCertificate
```

### 装上之后的行为（给用户交代清楚）

- **安装本身不弹 UAC**：装在 `%LOCALAPPDATA%\Programs\WhaleGirl`，不需要管理员。
- **只有缺 .NET 10 桌面运行时才弹一次 UAC**：安装器检测 `C:\Program Files\dotnet\shared\Microsoft.WindowsDesktop.App\10.*`，
  缺失就用 `ShellExec('runas')` 单独提权跑随包的安装包，装完复检；用户取消 UAC 会明确提示手动安装路径。
- 用户如果是**标准账号**（不是管理员），提权会失败，安装器会给出随包安装包的路径让用户找人代装；
  这种情况本来就装不了 .NET 运行时。
- 卸载时删掉安装目录，保留 `data\`（用户数据），并清掉 `runtime\dotnet` 里的 .NET 运行时安装包。

## 六、常见失败排查

| 现象 | 原因 / 处理 |
| --- | --- |
| `构建运行环境` 步骤红，日志有 `No matching distribution` | 依赖版本在 PyPI 上不存在或被 yank。改 `scripts/build-runtime.ps1` 的 `-Packages` 钉一个存在的版本，再改 `RUNTIME_CACHE_VERSION` |
| 同一个依赖装了老版本 | 缓存命中。改 `RUNTIME_CACHE_VERSION` 加一 |
| `找不到 ISCC.exe` | Inno Setup 下载失败且 chocolatey 兜底也失败。重跑；本机已装 Inno Setup 7 只对本机打包有效，CI 不用它 |
| `编译安装包` 红，日志里是 `Source file ... not found` | `.iss` 里引用的文件没生成（`launcher\publish\WhaleLauncher.exe`、`runtime\dotnet\…`）。看前一步 |
| 安装烟测红：`安装后缺文件` | `.iss` 的 `[Files]` 排除表把它排掉了，或某步没产出。按列出的文件名对 |
| 安装烟测红：`wheelhouse 不该在安装包里` | 排除表被改了 |
| 安装烟测红：包内 Python import 失败 | `build-runtime.ps1` 装依赖没收敛，看它第 4 步的轮次日志 |
| 签名步骤红：`找不到 signtool.exe` | runner 没带 Windows SDK。改成先装 SDK，或去掉签名 secrets 先出未签名包 |
| 签名步骤红：`PFX 解码失败` | `WINDOWS_SIGNING_PFX_BASE64` 不是纯 base64（带换行没事，带 `data:` 前缀不行） |
| Release 资产准备步骤红 | 对照版本号、CHANGELOG 与三个产物文件；修复构建后重跑，不能跳过检查直接公开 Release |

## 七、和本地打包脚本的关系

- `scripts/build-release.ps1` 还在，但**只用来打旧式的两个 zip**（源码包 / 完整包），不再产安装包。
- 安装包的一切（运行时、启动器、Inno 编译、签名、烟测）都在 CI 里，本机跑不了也不需要跑。
- 本地要验证安装包，从 Artifacts 下载即可；不要用本地 Inno Setup 复刻一遍，
  那样出来的包和 CI 的包不是同一个东西，签名也对不上。

> 本仓库**不提供**自签名 / 本机签名脚本：对外发的包只认公开受信任的签名（SignPath / OV / EV /
> Azure 可信签名）。自签名只对导入过证书的那台机器有效，别人下载还是「未知发布者」，
> 放在仓库里只会让人误以为「已经签好了」。
