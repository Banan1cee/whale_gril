# 微信消息后台发送

> 在不抢前台焦点的前提下，读取微信消息、切换会话、发送消息。

| 项 | 值 |
| --- | --- |
| 文档版本 | 1.0 |
| 实测日期 | 2026-10-27 |
| 实测环境 | Windows 10/11 中文版、微信 4.1.15.56（Qt 版）、DWM 合成桌面 |
| 验证方式 | 三轮实机测试，最高强度为 224 次前台窗口采样（每 100 ms 一次） |
| 结论 | 读、点、写三条通道全部可做到零焦点抢占 |

---

## 0. 摘要

微信 4.x 的界面是 **Qt 外壳 + MMUI 自绘渲染层**，控件树默认不对外暴露（只有 2 个节点）。常规自动化的做法是"热激活 + 真实键鼠 + OCR"，代价是抢前台、脆、慢。

本文记录另一条路：**三条互相独立的通道，全部通过 Windows 消息机制完成，不触发任何窗口激活。**

```
读：UIA 控件树（需要先物化）
点：PostMessage 鼠标消息（可穿透被遮挡的窗口）
写：伪造 WM_SETFOCUS + GBK 字节逐字节 WM_CHAR
```

实测结论：**224 次采样中，前台窗口从未变成微信。**

## 1. 能力矩阵

| 操作 | 手段 | 是否生效 | 是否抢前台 | 备注 |
| --- | --- | --- | --- | --- |
| 读取会话列表 / 消息 / 控件文本 | UIA `FindAll` | ✅ | ❌ | 需先物化控件树 |
| 切换会话 | `PostMessage` 鼠标点击 | ✅ | ❌ | 需先发 `WM_MOUSEMOVE` |
| 点击发送按钮 | `PostMessage` 鼠标点击 | ✅ | ❌ | 同上 |
| 写入英文 / 数字 | `WM_SETFOCUS` + 单字节 `WM_CHAR` | ✅ | ❌ | ASCII 本就是单字节 |
| 写入中文 | `WM_SETFOCUS` + **GBK 字节逐字节** `WM_CHAR` | ✅ | ❌ | 关键：不能用 UTF-16 码点 |
| 写入 emoji / GBK 外字符 | — | ❌ | — | 编码层不支持，需降级方案 |

## 2. 环境与前提

- **微信 4.x（Qt 版）**。3.x 是另一套架构，本文所有结论不适用。
- **中文区域设置**。写文字的编码依赖系统 ANSI 代码页（见 §4.7）。
- **同一登录会话**。跨会话（如 RDP 独立会话）需要另作处理。
- **微信窗口未最小化**。`IsIconic == False`。被遮挡没关系，最小化不行。
- 无需管理员权限，无需注入 DLL，无需修改微信任何文件。

## 3. 三条独立通道

### 3.1 读：UIA 控件树

微信启动后，UIA 树只有两个节点：

```
[Pane] Qt51514QWindowIcon  name='Weixin'
[Pane] MMUIRenderSubWindowHW
```

整个界面是自绘的，默认一棵"瘦身树"。必须先**物化**（见 §4.1），之后才能读到：

```
[Group] #MainView
  [ToolBar] #MainView.main_tabbar          ← 左侧导航
  [Group]   #MainView.main_window_corner_view
    [Custom] ...main_window_main_splitter_view
      [Custom] ...main_window_sub_splitter_view
        ...
[ListItem] '文件传输助手 [链接]…'          ← 会话列表项
[ListItem] '公众号 [2条] …'
[Edit]     #chat_input_field               ← 聊天输入框
[Button]   '发送'                           ← 发送按钮
```

物化后后代节点总数约 163 个（随会话数量浮动）。

### 3.2 点：PostMessage 鼠标消息

把鼠标消息直接投递到微信窗口的**消息队列**，绕过系统命中测试。被其他窗口完全遮挡时依然有效。

### 3.3 写：伪造焦点 + GBK 字节

先用一条 `WM_SETFOCUS` 让微信**以为**自己拿到了键盘焦点（只改 Qt 内部状态，不改系统前台窗口），然后逐字节投递 `WM_CHAR`。

## 4. 技术细节

### 4.1 让控件树物化

微信（准确地说是它用的 Qt）判断"是否有无障碍客户端在监听"，读的是系统参数 `SPI_GETSCREENREADER`。把它设成 `TRUE`，控件树就会物化。

```python
SPI_GETSCREENREADER = 0x0046
SPI_SETSCREENREADER = 0x0047
user32.SystemParametersInfoW(SPI_SETSCREENREADER, 0, ctypes.c_void_p(1), 0x01)
time.sleep(1.0)          # 实测 1~1.5 秒后树才长出来
```

实测效果：节点数 **2 → 163**，`chat_input_field`、会话列表、消息气泡全部出现。

> **✅ 2026-10-27 复核（同一台机器，微信 4.1.15.56）：结论成立，但补一条硬前提。**
>
> **前提：进程权限要和微信同级（管理员）。** 微信是提权进程时，普通权限的进程
> 调 UIA 读它的控件树会被 UIPI 挡掉 —— 现象是**0 个节点**，看着像「方案不成立」，
> 其实只是权限不够。提权重测立刻变成 **157 个节点**，`chat_input_field`、
> 发送按钮、会话列表全部读得到。这一条原文档没写，是最容易卡住人的地方。
>
> **别用 `SPI_GETSCREENREADER` 的读回值判断成败。** 实测即使树已经长出来
> （157 个节点、能读能发），`SPI_GETSCREENREADER` 读回**仍然是 0**；
> `SPI_SETSCREENREADER` 的返回值也不可靠（Python 里 FALSE、PowerShell 里 TRUE）。
> 唯一可信的判据是**数节点**（或直接看能不能找到 `chat_input_field`）。
>
> 复核时的实测量：
>
> | 项 | 值 |
> | --- | --- |
> | 节点数（提权后） | 157 |
> | `chat_input_field` | 读到，`.Name` = 当前会话名 |
> | 发送按钮中心 | (2410, 995)（2560×1600 屏，随窗口变） |
> | 前台在 6 个环节里变化的次数 | **0**（开标志 / 读控件 / 伪焦点 / 打字 / 点发送 / 收尾，全部 1181094 → 1181094） |
> | 发送耗时 | 2.6~3.2 秒/条（含切会话） |
>
> 顺带一个测量陷阱：如果脚本是**新开的提权控制台**里跑的，那个控制台窗口自己会把
> 前台抢走，于是「发送前前台 ≠ 发送后前台」—— 这不是微信抢的。判据要在同一个进程里
> 采样，或者干脆打印每个环节前后的前台（`examples/wechat_bg.py --probe` 就是这么干的）。
>
> 下面第 1、2、3 条注意事项本身仍然成立。

**这一条替代了传统的 `gate RVA` 扫描方案。** 后者要定位 `Weixin.dll` 里某个标志字节的偏移，每次微信小版本更新都可能失效，需要重新扫版本表。而 `SPI` 标志是系统级的，与微信版本无关。（本机 4.1.15.56 正好在版本表里扫不到，这条就是唯一还能用的物化路径。）

注意事项：

1. **必须还原**。这是全局系统标志，不还原会让所有应用都以为有屏幕阅读器在跑（可能带来性能开销）。推荐 `try/finally` 或上下文管理器。
2. **用 `FindAll` 而不是 `TreeWalker`**。这是最容易踩的坑：`TreeWalker` 逐层遍历时，中间层没物化就断了，只能拿到 62~67 个节点；`FindAll(Descendants)` 会强制请求全部后代，能拿到 163 个。
3. **不需要激活窗口**。物化、读取全过程都不需要窗口在前台，只需要它没被最小化。

### 4.2 控件标识

| 控件 | 标识 | 类型 | 支持的 Pattern |
| --- | --- | --- | --- |
| 聊天输入框 | `AutomationId = chat_input_field`，`ClassName = mmui::ChatInputField` | Edit | ValuePattern（读写）、TextPattern（读） |
| 搜索框 | `ClassName = mmui::XValidatorTextEdit` | Edit | ValuePattern（读写） |
| 会话列表项 | 无 AutomationId，靠 `Name`（含消息预览） | ListItem | SelectionItem、Invoke（**均为空壳**） |
| 发送按钮 | `Name = 发送`，`ClassName = mmui::XOutlineButton` | Button | Invoke（**空壳**） |
| 主窗口 | `ClassName = Qt51514QWindowIcon`，`Name = 微信` | Window | — |

`AutomationId = chat_input_field` 是稳定字符串，**不要用坐标或索引定位输入框**。

### 4.3 鼠标点击为什么能穿透

Windows 里键盘和鼠标是两套模型：

- **键盘**：程序会查 `GetKeyState()` / `GetKeyboardState()` 的真实状态，`WH_KEYBOARD` 钩子只在真实输入经过输入队列时触发。伪造的 `WM_KEYDOWN` 没有对应的钩子调用，程序一核对就穿帮（Raymond Chen 在 *The Old New Thing* 里反复讲过这一点）。
- **鼠标**：Qt 处理 `WM_LBUTTONDOWN` 时直接用消息里 `lParam` 携带的坐标，**不去查 `GetCursorPos()`**。所以坐标一给，它就当真。

必要条件有两个：

1. **坐标必须是客户区坐标**，不是屏幕坐标。用 `ScreenToClient` 转换。
2. **必须先发一条 `WM_MOUSEMOVE`**。Qt 维护一个"鼠标是否在窗口内"的状态位，只靠 `WM_MOUSEMOVE` / `WM_MOUSELEAVE` 更新。窗口被遮挡时系统不会送这两个消息，所以省略 `WM_MOUSEMOVE` 时点击会被丢弃。

消息序列：

```python
WM_MOUSEMOVE   = 0x0200
WM_LBUTTONDOWN = 0x0201
WM_LBUTTONUP   = 0x0202

pt = wintypes.POINT(screen_x, screen_y)
user32.ScreenToClient(hwnd, ctypes.byref(pt))
lp = (pt.y << 16) | (pt.x & 0xFFFF)

user32.PostMessageW(hwnd, WM_MOUSEMOVE,   0, lp)   # 必须
user32.PostMessageW(hwnd, WM_LBUTTONDOWN, 1, lp)   # wParam = MK_LBUTTON
time.sleep(0.07)
user32.PostMessageW(hwnd, WM_LBUTTONUP,   0, lp)
```

**实测：`InvokePattern.Invoke()` 和 `SelectionItemPattern.Select()` 都是空操作。** 微信的 MMUI 给所有控件统一生成了 UIA provider，属性（名字、位置、值）可读，但动作没人接——调用返回成功，界面毫无反应。不要在这两个 Pattern 上浪费时间。

### 4.4 为什么键盘不能直接穿透

不发 `WM_SETFOCUS` 而直接发 `WM_CHAR` 时，分两种情况：

| 场景 | 结果 |
| --- | --- |
| 微信在前台 | 字符能进去，但同时会激活窗口 —— 等于抢了焦点 |
| 微信在后台 | 字符被丢弃（Qt 的 `focusWindow` 为 null），但窗口仍会被激活 |

所以"直接发 `WM_CHAR`"既做不到后台，也保不住焦点。

### 4.5 伪造 WM_SETFOCUS

`WM_SETFOCUS`（0x0007）的作用是通知窗口"你现在有键盘焦点了"。手动投递一条，Qt 内部的焦点状态就变了，后续的 `WM_CHAR` 开始被接受——**而系统前台窗口完全没有变化**。

```python
user32.PostMessageW(hwnd, 0x0007, 0, 0)   # WM_SETFOCUS
time.sleep(0.10)
# 之后逐字节发 WM_CHAR
```

这个技巧在 Raymond Chen 2025 年那篇 *You can't simulate keyboard input with PostMessage, revisited* 的评论区中被提到过（用户 `許恩嘉`）：*"I sent it a fake WM_SETFOCUS message, which successfully fooled it."*

### 4.6 WM_ACTIVATE 是雷区

看起来更"完整"的做法是连窗口激活状态一起伪造：

```python
user32.PostMessageW(hwnd, 0x0006, 1, 0)   # WM_ACTIVATE —— 千万不要发
```

**实测：发了 `WM_ACTIVATE` 之后，窗口真的会被激活到前台。** 伪焦点能骗，伪激活不能。整个方案会因此失效。

### 4.7 编码：GBK 字节流

这是最容易踩的坑，也是唯一需要理解原理的地方。

**现象**：直接发 UTF-16 码点会乱码。

```python
# 错误做法
for ch in "鲸":               # U+9CB8
    PostMessage(hwnd, WM_CHAR, ord(ch), 1)
# 输入框里出现的是 '笢'（U+7B22）
```

**原因**：微信把 `WM_CHAR` 的 `wParam` 按 **GBK 字节流**解释，而且是**低字节优先**。

推演验证（全部实测）：

| 投递的 wParam | 内存字节（小端） | GBK 解码 | 结果 |
| --- | --- | --- | --- |
| `0x9CB8`（`鲸` 的 UTF-16） | `[B8, 9C]` | `GBK[B8 9C]` | `笢` |
| `0xBEA8` | `[A8, BE]` | `GBK[A8 BE]` | `ň` |
| `0xA8BE` | `[BE, A8]` | `GBK[BE A8]` | `鲸` ✅ |
| `0xBE` 后接 `0xA8`（分两次） | `[BE]`、`[A8]` | `GBK[BE A8]` | `鲸` ✅ |

而 `鲸` 的 GBK 编码正是 `BE A8`，`中` 是 `D6 D0`。

**正确做法**：先 `encode('gbk')`，然后把每个字节单独投递一次。

```python
payload = text.encode("gbk")        # '鲸' -> b'\xbe\xa8'
for b in payload:
    user32.PostMessageW(hwnd, WM_CHAR, b, 1)   # wParam = 0xBE，然后 0xA8
    time.sleep(0.04)
```

单字节投递时 `wParam` 的高字节是 0，不会引入多余字符；微信会把连续投递的字节累积起来，凑够一个完整 GBK 字符再上屏。

**另外两个字符消息不可用**：

- `WM_IME_CHAR`（0x0286）：同样把 wParam 当 GBK，但**字节序相反**（`0x9CB8` 得到 `湼`），且实测对多字节字符同样不可靠。
- `WM_UNICHAR`（0x0109）：完全无效，字符不出现。

### 4.8 坐标转换

UIA 返回的 `BoundingRectangle` 是**物理像素屏幕坐标**。`PostMessage` 的 `lParam` 需要**客户区坐标**。

```python
def click_screen(hwnd, sx, sy):
    pt = wintypes.POINT(int(sx), int(sy))
    user32.ScreenToClient(hwnd, ctypes.byref(pt))
    lp = (pt.y << 16) | (pt.x & 0xFFFF)
    ...
```

**DPI 注意**：如果宿主进程不是 DPI-aware，`ScreenToClient` 的结果会被 DPI 虚拟化影响，坐标对不上。建议在进程启动时声明 DPI 感知，或用 `SetThreadDpiAwarenessContext(-4)`（`PER_MONITOR_AWARE_V2`）包裹相关调用。

实测环境：2560×1600 物理 / 1707×1067 逻辑（150% 缩放）。未声明 DPI 感知时坐标会整体偏移。

### 4.9 为什么必须发 WM_MOUSEMOVE

Qt 的 `QWindow` 维护 `m_mouseInside` 状态：

- `WM_MOUSEMOVE` 进入窗口范围 → 置为 true
- `WM_MOUSELEAVE` 离开 → 置为 false

窗口被遮挡时，系统不会送这两个消息，`m_mouseInside` 一直是 false。此时投递 `WM_LBUTTONDOWN`，Qt 会因为"鼠标不在窗口内"而忽略。

先发一条 `WM_MOUSEMOVE`，把状态位骗成 true，后续点击才会被处理。

### 4.10 收尾

输入完成后补一条 `WM_KILLFOCUS`，把伪造的焦点状态清掉，避免影响后续的界面判断：

```python
user32.PostMessageW(hwnd, 0x0008, 0, 0)   # WM_KILLFOCUS
```

## 5. 完整实现

### 5.1 发送端（纯 ctypes，零依赖）

```python
"""微信消息后台发送 —— 零依赖核心实现"""

import ctypes
import time
from ctypes import wintypes

user32 = ctypes.WinDLL("user32", use_last_error=True)

# 消息常量
WM_SETFOCUS    = 0x0007
WM_KILLFOCUS   = 0x0008
WM_CHAR        = 0x0102
WM_MOUSEMOVE   = 0x0200
WM_LBUTTONDOWN = 0x0201
WM_LBUTTONUP   = 0x0202

# 系统参数
SPI_GETSCREENREADER = 0x0046
SPI_SETSCREENREADER = 0x0047
SPIF_UPDATEINIFILE  = 0x01

# 原型声明（64 位必须，否则参数会被截断）
user32.PostMessageW.argtypes = [
    wintypes.HWND, wintypes.UINT, wintypes.WPARAM, wintypes.LPARAM
]
user32.PostMessageW.restype = wintypes.BOOL
user32.ScreenToClient.argtypes = [wintypes.HWND, ctypes.POINTER(wintypes.POINT)]
user32.ScreenToClient.restype = wintypes.BOOL
user32.FindWindowW.argtypes = [wintypes.LPCWSTR, wintypes.LPCWSTR]
user32.FindWindowW.restype = wintypes.HWND
user32.GetForegroundWindow.restype = wintypes.HWND
user32.SystemParametersInfoW.argtypes = [
    wintypes.UINT, wintypes.UINT, ctypes.c_void_p, wintypes.UINT
]
user32.SystemParametersInfoW.restype = wintypes.BOOL


def find_wechat():
    """按窗口标题找微信主窗口。类名 Qt51514QWindowIcon 会随 Qt 版本变化，用标题更稳。"""
    hwnd = user32.FindWindowW(None, "微信")
    if not hwnd:
        raise RuntimeError("没找到微信主窗口，确认微信已登录且未最小化")
    return hwnd


class ScreenReaderFlag:
    """临时打开系统屏幕阅读器标志，让微信物化 UIA 控件树。"""

    def __enter__(self):
        self._prev = ctypes.c_uint(0)
        user32.SystemParametersInfoW(
            SPI_GETSCREENREADER, 0, ctypes.byref(self._prev), 0
        )
        user32.SystemParametersInfoW(
            SPI_SETSCREENREADER, 0, ctypes.c_void_p(1), SPIF_UPDATEINIFILE
        )
        time.sleep(1.0)          # 等控件树长出来
        return self

    def __exit__(self, *exc):
        user32.SystemParametersInfoW(
            SPI_SETSCREENREADER, 0, ctypes.c_void_p(self._prev.value), SPIF_UPDATEINIFILE
        )


class WeChatSender:
    """只做三件事：点、写、收尾。全部不抢前台。"""

    def __init__(self, hwnd=None):
        self.hwnd = hwnd or find_wechat()

    @staticmethod
    def _lparam(x, y):
        return (y << 16) | (x & 0xFFFF)

    def click_screen(self, sx, sy, settle=0.07):
        """在屏幕坐标处点击微信窗口。被遮挡也有效。"""
        pt = wintypes.POINT(int(sx), int(sy))
        if not user32.ScreenToClient(self.hwnd, ctypes.byref(pt)):
            raise ctypes.WinError(ctypes.get_last_error())
        lp = self._lparam(pt.x, pt.y)
        user32.PostMessageW(self.hwnd, WM_MOUSEMOVE, 0, lp)      # 必须，否则被丢弃
        user32.PostMessageW(self.hwnd, WM_LBUTTONDOWN, 1, lp)
        time.sleep(settle)
        user32.PostMessageW(self.hwnd, WM_LBUTTONUP, 0, lp)

    def type_text(self, text, char_gap=0.04):
        """向当前会话输入框注入文本。返回 False 表示编码不支持。"""
        try:
            payload = text.encode("gbk")
        except UnicodeEncodeError:
            return False
        user32.PostMessageW(self.hwnd, WM_SETFOCUS, 0, 0)
        time.sleep(0.10)
        for b in payload:
            user32.PostMessageW(self.hwnd, WM_CHAR, b, 1)
            time.sleep(char_gap)
        return True

    def end_input(self):
        user32.PostMessageW(self.hwnd, WM_KILLFOCUS, 0, 0)

    def send_text(self, text, send_button_xy):
        """输入 + 点发送。send_button_xy 是 (屏幕x, 屏幕y)。"""
        if not self.type_text(text):
            raise ValueError(f"GBK 无法编码: {text!r}")
        time.sleep(0.35)                               # 等按钮变 enabled
        self.click_screen(*send_button_xy)
        time.sleep(0.40)
        self.end_input()


if __name__ == "__main__":
    fg_before = user32.GetForegroundWindow()
    with ScreenReaderFlag():
        sender = WeChatSender()
        # 发送按钮的屏幕坐标需要用 UIA 先读出来（见 5.2）。
        # 下面是本机实测时的值，换机器会变，仅作占位。
        send_xy = (2490, 1499)
        sender.send_text("1", send_xy)
    fg_after = user32.GetForegroundWindow()
    assert fg_before == fg_after, "前台被抢了！"
```

## 7. 失败方案清单

以下全部实机试过，**不要重复踩**。

| 方案 | 结果 | 原因 |
| --- | --- | --- |
| `ValuePattern.SetValue` | 有效但**抢前台** | 微信在该 API 内部主动激活窗口 |
| `InvokePattern.Invoke()`（发送按钮） | **空操作** | MMUI 只实现了读属性，动作没人接 |
| `InvokePattern.Invoke()`（会话项） | **空操作** | 同上 |
| `SelectionItemPattern.Select()` | **空操作** | 同上 |
| 真实鼠标点击（窗口被遮挡） | **点不到** | 系统命中测试落到遮挡窗口上 |
| 真实鼠标点击（先激活窗口） | 有效但抢前台 | 绕不开 |
| `PostMessage WM_CHAR`（不伪造焦点） | 字符进不去 / 窗口被激活 | Qt 的 focusWindow 为 null |
| `SendMessage WM_CHAR`（同步版） | 有效但抢前台 | 同步调用会触发窗口激活 |
| `WM_CHAR` 发到 `MMUIRenderSubWindowHW` 子窗口 | **无效** | 消息要发给顶层窗口，由 Qt 路由 |
| `WM_PASTE`（无伪造焦点） | **无效** | 输入框没有焦点，不处理粘贴 |
| `WM_PASTE`（伪造焦点后） | **无效** | 实测仍不生效 |
| `WM_UNICHAR` | **无效** | 不支持 |
| `WM_IME_CHAR` | 乱码 | 字节序与 `WM_CHAR` 相反 |
| `WM_CHAR` 发 UTF-16 码点 | 乱码 | 见 §4.7 |
| `WM_KEYDOWN + WM_CHAR + WM_KEYUP` | 有效但抢前台，且字符重复 | `WM_KEYDOWN` 本身也会产生字符 |
| `WM_ACTIVATE` + `WM_SETFOCUS` + `WM_CHAR` | 有效但抢前台 | `WM_ACTIVATE` 会真的激活窗口 |
| `WS_EX_NOACTIVATE` + `WM_CHAR` | 有效但**仍抢前台** | 微信是在处理字符输入时自己调用的激活，不走窗口激活路径 |
| `WS_EX_NOACTIVATE` + `SetValue` | 有效但**仍抢前台** | 同上 |
| `SPI_SETSCREENREADER` 后继续用 `TreeWalker` | 只拿到 62~67 节点 | 懒加载断开，必须用 `FindAll` |

## 8. 限制与风险

### 8.1 编码限制

- **GBK 覆盖范围之外的字符无法发送**：emoji、部分生僻字、日文假名的一部分。`"🚀".encode("gbk")` 直接抛 `UnicodeEncodeError`。
- 遇到这类字符需要降级路径（拆成纯文本部分 + 跳过，或退回会抢焦点的 `SetValue`）。

### 8.2 代码页依赖

微信把 `WM_CHAR` 按 **系统 ANSI 代码页** 解释。本文所有结论建立在**中文系统（代码页 936 / GBK）**上。

如果部署在英文系统（代码页 1252），中文将无法注入；日文系统（932）则需要换成 Shift-JIS。**移植时必须重新验证编码路径。**

### 8.3 微信更新风险

- `AutomationId = chat_input_field` 是内部标识，大版本更新可能改。
- `MMUI` 的字符处理如果从 ANSI 改成 Unicode，§4.7 的整个编码方案会失效。
- `SPI_SETSCREENREADER` 这条物化路径依赖 Qt 的无障碍检测行为，如果微信换成自研检测机制，也会失效。

**建议**：把这些点做成运行时自检（发一个已知字符读回校验），而不是写死假设。

### 8.4 风控视角

- 读路径读的是 UIA 控件树，**不产生任何网络或文件痕迹**，微信侧看不到。
- 写路径投递的是伪造窗口消息。与真实键鼠操作相比，缺少硬件输入时间戳和 `GetCursorPos` 的变化，理论上可被识别。
- 鼠标点击的**时间分布**仍然完全由调用方控制，拟人节奏依然有效。
- 综合判断：风险低于 Hook 注入，与"真实键鼠 + 拟人节奏"大致相当，但**不是零**。

### 8.5 其它

- **不能跨会话**。这套机制作用于当前桌面的窗口消息队列，独立 RDP 会话（`CreateDesktop` / 多用户）需要另作处理。
- **窗口不能最小化**。`IsIconic == True` 时控件树不物化。
- **同一时刻只能有一个伪造焦点持有者**。如果多个进程同时操作同一个微信窗口，焦点状态会互相干扰。

## 9. 排错

| 现象 | 排查方向 |
| --- | --- |
| 控件树只有 2 个节点 | `SPI_SETSCREENREADER` 没设置 / 设置后等待不足 1 秒 / 微信已最小化 |
| 只能拿到 62~67 个节点 | 用了 `TreeWalker`，改用 `FindAll(Descendants)` |
| 找不到 `chat_input_field` | 控件树没物化；或当前不在聊天页 |
| 点击没反应 | ①坐标没转客户区 ②没发 `WM_MOUSEMOVE` ③坐标算错（DPI） |
| 点击落到了别的会话 | 坐标是屏幕坐标却当成了客户区坐标，或 DPI 虚拟化偏移 |
| 文字写不进去 | 没发 `WM_SETFOCUS`；或发送间隔太短（建议 ≤ 45ms/字节） |
| 中文变成乱码 | 用了 UTF-16 码点，改成 GBK 逐字节 |
| 部分字符丢失 | 字节间隔太短，加大到 40~50ms |
| 发送按钮点不动 | 输入框为空时按钮 `IsEnabled == False`，先写入内容再等 350ms |
| 操作后前台变了 | 检查是否误发了 `WM_ACTIVATE`（0x0006） |
| 关掉程序后其它应用异常 | `SPI_SETSCREENREADER` 没还原，手动设回 0 或重启 |

### 10.1 与本项目历史问题的关系

本方案**不调用** `SetWindowPos`、`SetForegroundWindow`、`SetFocus`、`SetCursorPos`、`SendInput` 中的任何一个。因此它绕开了本项目此前踩过的两个坑。

**① 非 ASCII 安装路径**

旧方案依赖 `ensure_window()` 把窗口从最小化恢复到前台，内部走 `SetWindowPos`。在中文路径下 Qt accessibility 热激活失败，之后每条回复都报 `error(5, 'SetWindowPos', '拒绝访问')`。

本方案只要求窗口 `IsIconic == False`，既不移动窗口也不改变 Z 序；物化走系统级 `SPI_SETSCREENREADER`，与安装路径无关。

**② 桥接与微信的完整性级别不一致**

这是本方案唯一保留的硬约束。

当次实测环境：**桥接进程与微信进程同为 Medium 完整性级别（普通用户）**，`PostMessageW` 全部返回成功。

`PostMessage` 走的是窗口消息，同样受 UIPI 约束。向**更高**完整性级别的进程投递会失败，表现为 `PostMessageW` 返回 `FALSE` 且 `GetLastError() == 5`（`ERROR_ACCESS_DENIED`）。如果微信被以管理员身份启动而桥接是普通权限，所有消息投递都会静默失败，表现为"什么都没发生"。

排查方法：

```python
if not user32.PostMessageW(hwnd, WM_SETFOCUS, 0, 0):
    err = ctypes.get_last_error()
    if err == 5:
        raise RuntimeError("权限不一致：微信的完整性级别高于桥接，请让两边一致")
```

**本方案比旧方案更不容易触发这个问题**——旧方案必须调用 `SetWindowPos` / `SetForegroundWindow`，这两个 API 被 UIPI 拦截后就是直接报错；本方案只要两边权限相同就能工作，不需要提权。

## 12. 本机复测：微信 4.2.0.9 的四个补丁

本文档的实测环境是 4.1.15.56。搬到 **微信 4.2.0.9**（Windows 11、150% 缩放、提权运行）
时又踩到四个新坑，`bridge/bg_sender.py` 里都已经处理：

### 12.1 DPI：不声明感知会点偏 1.5 倍（最坑的一个）

UIA 的 `BoundingRectangle` 是**物理像素**，而 DPI 不感知的进程里 `ScreenToClient`
拿到的是**逻辑像素**。本机 150% 缩放，两者差 1.5 倍 —— 表现为「点了会话行，
页面变了，但输入框消失、发送按钮也没了」，看起来像「控件树坏了」。

修法：进程启动时 `SetProcessDpiAwarenessContext(PER_MONITOR_AWARE_V2)`；
切不动时退回 `PhysicalToLogicalPointForPerMonitorDPI` 手动换算。

### 12.2 gate 字节：必须 0→1，不能只写 1

`wechatauto.accessibility.wake(verify=True)` 用「顶层窗口类名是否以 `mmui::` 开头」
判断成功。4.2 的主窗类名**本来就是** `mmui::MainWindow`，于是它每次都报「树已物化」，
实际 `FindAll(Descendants)` 只有 1 个节点。

而且微信进程跑久了，gate 字节会停在 1、树却是空的；这时**再写一次 1 没用**，
必须先归零再置 1，Qt 才会重新走一遍无障碍初始化。

`bg_sender._gate_pulse()` 因此改成自己写字节、再用**节点数**验证，不信类名。

### 12.3 窗口隐藏（不是最小化）也会让树萎缩

微信缩到托盘时主窗 `visible=False`、`IsIconic=False`，此时 `FindAll(Descendants)`
只有 1 个节点。用 `ShowWindow(SW_SHOWNOACTIVATE)` 显示出来即可，
**实测前后前台窗口号不变**。这比 §8.5 的「最小化就不发」更宽容，且仍然不抢焦点。

### 12.4 点会话行后控件树会重建

点一次会话，节点数会短暂从 150 掉到 81（输入框暂时消失），约 0.5 秒恢复。
`open_chat()` 里加了「节点数掉下去就补一次物化」的重试，不要立刻判失败。

另外输入框的 `Name` 有时带鼠标提示（`文件传输助手长按鼠标 语音输入`），
`norm_chat_name()` 会切掉这些尾巴，否则会误判成「不在目标会话」。

| 发送一条消息 | **2.0 秒**（10 个汉字，`charGapMs=40`） |
| 发送前 / 后前台窗口 | 200612 / 200612 |

### 12.6 仍然存在的前提

- **必须提权**：非管理员进程读 4.2 的控件树是 0 个节点（UIPI）
- 微信不能缩在托盘；`bgSend.unhideWindow=true`（默认）会自动「显示但不激活」
- 群聊真 @（UIA 选人）和引用回复仍然走旧通道，这两种会抢前台
